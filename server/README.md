# SALEANE local authority

This is a local V1 candidate. The application runs on one address with a Node HTTP API and SQLite on the same computer. The server, rather than a browser tab, owns signed-in workspace changes. Browser demo mode remains separate. No payment provider is connected. Appointment emails and texts run through an outbox that stays in test mode, sending nothing, until a provider is configured (below).

## Run and configuration

Use the installed Node 22.22 runtime and existing project dependencies. `npm run dev` serves the UI and API together at `http://127.0.0.1:5173`. `npm run build` creates the application and standalone server; `npm start` runs that built application. Stop the development host before starting the built host on the same port. `npm run preview` previews static UI only and does not provide this API.

| Setting       | Default                                                         | Purpose                                                                                 |
| ------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `APP_ORIGIN`  | `http://127.0.0.1:5173`                                         | Exact browser origin, including port; writes require it and requests must use its Host. |
| `PORT`        | `5173`                                                          | Standalone listening port, 1024–65535. Development uses fixed port 5173.                |
| `DB_PATH`     | `.saleane-data/saleane.sqlite` in the current project directory | Durable local database; keep it outside static files and Git.                           |
| `STATIC_ROOT` | `dist`                                                          | Built standalone UI directory.                                                          |

Optional bot check: set both `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` (Cloudflare Turnstile) to let a studio switch on a check before public holds. Without both keys the check is unavailable and the studio setting cannot be switched on; if keys are removed after a studio switched it on, holds proceed without the check until keys return. With them, the standalone host's content security policy also allows `https://challenges.cloudflare.com` for the widget script and frame. Cloudflare's test keys (`1x00000000000000000000AA` and `1x0000000000000000000000000000000AA`) always pass and suit local review.

The standalone host binds only `127.0.0.1`. It does not implement TLS, a reverse proxy, public hosting, background jobs or remote access. HTTPS origins require a separately qualified TLS host. `createApiHandler({origin,databasePath,now?,allowRegistration?})` is callable Node request/response middleware; registration can be disabled through its options. `.inject()` exercises the same handler without listening on a network port. `.close()` releases SQLite. Development middleware and standalone hosting must not run duplicate application servers.

### Appointment messages (PILOT-01)

The server plans booking confirmations, new-time notices, reminders and cancellation notices for real (non-sample) studios every 30 seconds and shortly after any change. Each message is recorded once in the `outbox` table, keyed by visit, kind, channel and visit time, so a restart or repeat pass cannot send it twice. Before it leaves, the visit and the client's choices are checked again; a visit that changed is skipped. The row is marked "unclear" before the provider is called, so a crash mid-send never causes a silent second copy. Busy providers are retried up to three times; an unclear outcome waits for staff to choose "Send again". Only a verified provider receipt marks a message delivered. The stored text keeps a placeholder where the private manage link goes; each message gets a fresh link (the newest four message links per visit stay open, and a desk or booking link still closes them all).

| Setting                                                  | Default | Purpose                                                                                                           |
| -------------------------------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------- |
| `SALEANE_EMAIL_PROVIDER`                                 | `test`  | `test` writes emails down and sends nothing; `postmark` sends through Postmark.                                   |
| `POSTMARK_SERVER_TOKEN`, `SALEANE_EMAIL_FROM`            | unset   | Required for `postmark`; the from address must be a verified Postmark sender.                                     |
| `POSTMARK_WEBHOOK_SECRET`                                | unset   | Basic-auth password set on the Postmark delivery and bounce webhook pointing at `/api/hooks/postmark`.            |
| `SALEANE_SMS_PROVIDER`                                   | `test`  | `test` writes texts down and sends nothing; `twilio` sends through Twilio.                                        |
| `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM` | unset   | Required for `twilio`. `TWILIO_FROM` is a sending number or a Messaging Service SID (`MG…`). Receipts are signed. |

STOP and START (Stage 1): a text to the studio's line that is only one of the phone networks' opt-out words turns texts off for every client on that number, recorded on their timeline as their own choice, and adds the number to the studio's `textStops` list, client or not. Nothing is texted to a listed number (the outbox checks again just before anything leaves) until it texts START, which turns back on only the texts a STOP turned off; texts turned off at the desk stay off and the client's page says they asked. A text never changes email or email news. Turning texts back on at the desk for a client who replied STOP needs `askedAfterStop: true` on `contact-preferences`. In test mode, `POST /workspaces/:orgId/test-text` delivers a text on this computer so all of this can be seen working.

Messages to clients (Stage 4): when the owner approves a message to clients (`news-approve`), the server counts its clients again, with erasure requests from the audit log, and refuses the approval if the numbers differ from the ones the owner saw. In the same transaction it writes one `news` outbox row per person (keyed by message and client, so a repeated approval adds nothing), due from the next 09:00 to 19:00 window on the studio's clock. Visit messages go first in each batch of 50. Just before each copy leaves, the outbox checks again that the message is still approved, the client still agrees, has not replied STOP, has no erasure request and can still be reached that way, and that it is daytime; a copy that could not go within three days of approval is skipped. `news-stop` marks every waiting copy skipped. Each email carries its own stop link (`/news/stop#token`, only the hash kept in `news_links`, migration 33, for 400 days, retired when the client's email changes), goes on Postmark's `broadcast` stream with a `List-Unsubscribe` header, and needs a button press, so a mail scanner opening the link changes nothing. Texts end with "Reply STOP to stop texts." Sample studios never queue. A copy of a message to clients is sent again only by the owner.

Naming a live provider without all of its keys stops the server at start rather than falling back. The Postmark and Twilio adapters follow each provider's published API and are covered by tests with simulated responses; they have not yet run against a real account. Receipts need a public HTTPS address, so they only arrive once the app is hosted.

### Account emails (NEXT-03)

Password and email confirmation links go through the same email provider as appointment messages. Each email is recorded in `account_mail` before the answer goes back, as `unknown` until the provider answers; in test mode nothing is sent and it ends as `test`. When the origin is this computer (127.0.0.1, localhost or ::1) the server writes the link to its log (`[SALEANE] Email is not connected, so this reset link was not sent to …`) for whoever runs it; on any other origin the link is never written anywhere, and the answers say so with `linkInLog: false`. The code travels in the address fragment (`/reset-password#…`), so browsers never send it to a server or in a Referer. Links are stored only as hashes and work once (checked inside the transaction that acts on them). Earlier links of the same kind keep working until they expire or one of them is used, since emails can arrive out of order; using one retires the rest. They also stop working if the account email changes or the database is restored from a backup. One account gets at most five links of each kind an hour. Emails go out after the answer, so a slow provider never delays sign-up and the forgot answer takes the same time whether or not the address has an account.

### Two-step sign-in (NEXT-04)

Time-based codes from any authenticator app (RFC 6238: SHA-1, six digits, 30 seconds, one step either side of now), worked out on this server with no outside service. The key is kept in `accounts.totp_secret` once a code from the app confirms it, and every accepted step is remembered so a code never works twice. Ten recovery codes are shown once and stored only as SHA-256 hashes; each works once. With two-step sign-in on, `POST /auth/login` and `POST /auth/reset` answer `{twoStep:true,challenge}` and set no cookie; the challenge lasts five minutes and five wrong codes, and `POST /auth/login/code` finishes signing in (410 when it must start again). Turning it on signs out every other session; turning it off or making new recovery codes needs the password; each change, and each recovery code used, is emailed to the account. A password reset or change also ends any sign-in still waiting for its code. Restoring a backup removes open sign-in steps and unfinished set-ups, and retires every recovery code it brings back, since one may have been used since the backup; the person makes new ones (Settings warns that none are left). Keys sit in SQLite like connection secrets, so a hosted database should encrypt them at rest.

### Who changed what (NEXT-05)

Every saved change already wrote an `audit_events` row with who made it and when. Migration 25 adds `detail`: when a change is saved, `persist` compares the record it was about before and after (or the settings it changed) and keeps the names of the details that changed, with the before and after values only for numbers, money, times, dates, yes-or-no settings and links between records. Client records, consultations, forms, messages and other records about a person keep only which details changed, and no typed wording is ever kept. New money records keep their amounts and method. `GET /workspaces/:orgId/changes` turns the entries into plain words for the owner, resolving names from the current studio record. The privacy record asks `/audit` for its own kinds, so a busy studio's other changes never push them out of its list.

### Help requests (NEXT-06)

Anyone signed in can write to the SALEANE team from Help. `POST /support` keeps the request in `support_requests` (migration 28) first, with the account, the studio they were in (checked against their own memberships), their role there and the screen they were on, then emails it to `SALEANE_SUPPORT_EMAIL` through the email provider the studio messages use, from "SALEANE Help". The row then says what happened: `kept` (no help address set; the server log says so), `test` (email in test mode, so not sent), `accepted` by the email service, `failed`, or `unknown`. Never show a request as sent unless the email service accepted it; nobody is recorded as having read it. Five requests an hour for each person, and ten an hour from one address. Rows are never deleted here.

| ----------------------- | ------- | --------------------------------------------------------------------------------------------------------------- |
| `SALEANE_SUPPORT_EMAIL` | unset   | Where help requests are emailed. Unset keeps them on the server. Must be an email address, or the server stops. |

### Charging studios (NEXT-02)

Each real studio gets a `studio_plans` row when it is made: a 14-day trial with no card. Sample studios never get one and are never charged. `billing.run()` runs every minute (with the outbox) and, for each plan not held by a restore: emails the owner three days before a trial ends; ends a trial (charging the first month, or read only with no card); renews a paid month on its day; retries a declined bill 1, 3 and 7 days after it first failed; and makes the studio read only 14 days after that. A month is billed in advance for every open location, with Plus if chosen and VAT at 20% for UK studios (US sales tax is left to the card service). Plus switched on in a paid month is a separate bill for the part of the month left (nothing under £1); switched off, it lasts to the end of the month.

Bills are numbered `TEST-000001` in test mode and `SAL-000001` otherwise. Before the card service is asked, the bill is claimed (`open` → `charging`) with the key `<billId>.<attempt>`, which is also the card service's idempotency key; an unclear answer stays `charging` and is asked about again with the same key after ten minutes, and nothing more is taken from that studio until it is known. Only one month bill can be live for a studio and month (a unique index), and `run()` never overlaps itself.

While a studio is read only, `billing.guard` refuses every write under `/api/workspaces/:id/` with 402 and `readOnlyMessage`, except the plan itself, privacy exports and erasure requests, removing someone (`membership` with role `remove`), revoking access keys and guest links, and pausing connections. Reads, downloads and the public booking page carry on, and the AI allowance is nought. Nothing is deleted. Thirty days after the last day paid for (`lock_at`: the missed payment, or the end of the trial or plan), `billing.run()` locks the studio (`locked_at`, `billing.locked`, one email to the owner): `billing.guard` then refuses everyone but the owner with 402 and `lockedMessage`, even to read; the owner keeps the studio record, the plan, privacy exports and the safety actions above; the public booking pages and the AI receptionist answer 404, and access keys 402. Guest manage links keep working for bookings already made. A paid month clears both. Restoring a backup marks open and charging bills `unknown` ("check with the card service before charging again") and sets `held_at` on every plan. Nothing is charged by itself, and the owner cannot pay or add Plus (409), until the next `billing.run()` has asked the card service for every charge carrying the studio's mark (`metadata[studio]`; Stripe's search, page by page). A bill it took is marked paid without a second receipt; one made after the backup is put back from the marks its charge carries (period, kind, number, amounts), keeping its number when it is free; a bill it did not take is owed again (or cancelled when it was Plus, the studio is read only, or a later month was paid), and the next attempt uses a key past every one the card service has seen. Then `held_at` is cleared and the plan carries on. While a charge is still processing, or the card service cannot be asked, the plan stays held and is asked about again each minute. Test mode never takes money, so the check finds nothing and releases at once.

| Setting                                                      | Default | Purpose                                                                                                                                                                                               |
| ------------------------------------------------------------ | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SALEANE_BILLING_PROVIDER`                                   | `test`  | SALEANE's own card account for charging studios, separate from `SALEANE_PAYMENTS_PROVIDER`. `test` uses the labelled test card page at `/billing/test-card` and moves no money; `stripe` uses Stripe. |
| `BILLING_STRIPE_SECRET_KEY`, `BILLING_STRIPE_WEBHOOK_SECRET` | unset   | Required for `stripe`. The webhook points at `/api/hooks/stripe-billing`. The adapter follows Stripe's published API and has not run against a real account.                                          |

### Card payments (PILOT-02)

One payment provider takes card payments for the whole server. Every payment starts as a row in `payment_attempts` (deposit, checkout balance, missed visit fee, saved card or refund) and enters the studio record only when the provider confirms it, inside one transaction with the attempt's new state. Before a card is charged the ledger command is rehearsed, so a charge is attempted only when it will land; if the record changes while the card is out (a visit cancelled mid-payment), the attempt is marked `review` with what happened instead of being forced in. Desk requests carry an `Idempotency-Key`, and the attempt's own ID is sent to the provider as its idempotency key, so a repeated click or dropped connection cannot charge twice. Card numbers never reach SALEANE: guests use the provider's own page, and staff charge a card the provider saved or a reader the provider runs. `saved_cards` keeps only the provider's references, brand, last four digits, expiry and the exact terms the guest agreed to; removing a card detaches it at the provider and keeps the row with a removal time. Client commands that name the `card` method or a processor are refused (403). An unclear provider answer (a dropped connection, a Stripe server error or an idempotency clash) is kept as `unknown` and blocks any new charge or refund for the same visit or payment until staff choose "Check again", which repeats the exact request under the same idempotency key. A guest's payment page closes after 30 minutes, or as soon as they come back without paying, and only one can be open per visit.

| Setting                                      | Default | Purpose                                                                                                               |
| -------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------- |
| `SALEANE_PAYMENTS_PROVIDER`                  | `test`  | `test` uses SALEANE's labelled test payment page and test card reader, and moves no money; `stripe` uses Stripe.      |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | unset   | Required for `stripe`. A `sk_test_` key keeps Stripe in its own test mode. The webhook points at `/api/hooks/stripe`. |
| `STRIPE_READERS`                             | unset   | Card readers for checkout, as `readerId:Label,readerId:Label` (Stripe Terminal server-driven readers).                |

The Stripe adapter follows Stripe's published API (Checkout for guests, off-session PaymentIntents for saved cards, server-driven Terminal readers, refunds, `Stripe-Signature` webhooks with a five-minute tolerance) and is covered by tests with simulated responses; it has not run against a real account. Webhooks need a public HTTPS address, so card readers and guest payments can only be confirmed by Stripe once the app is hosted. Tap to Pay on a phone needs a native phone app and is not part of this web candidate.

### Memberships paid from a saved card (Stage 1)

A membership can be paid each month from a card the client saved. The owner, a manager, or the general manager of the location that sold it, picks one of the client's saved cards on their page, reads them the exact words ("{Client} agrees that {Studio} may take {£X} from their {Visa} card ending {1234} on the {9th} of each month for {Membership}, until they cancel. They will get a reminder three days before each payment.") and confirms they agreed. `POST /workspaces/:orgId/plan-cards/:holdingId` checks the card is this client's, still saved and saved with this server's provider, works the words out again and refuses any difference, and keeps the card, words, time and person on the membership (`cardAgreements`). Page commands can never name a card, set this up or note a decline (403). The first month taken from the card is the first due date at least three days away; earlier months are paid at the desk as before. Turning it off, removing the card or ending the membership closes the agreement and is recorded.

`server/payments/memberships.ts` runs a loop in the outbox's style (started with the outbox interval, nudged after writes, `api.memberships.tick()` in tests). Each pass queues a `plan_reminder` through the outbox three days before each payment, between 09:00 and 19:00 studio time, once per membership, month and channel (email whenever the client has an address, text only when the studio sends texts and the client allows them); in test mode the outbox writes it down and never claims it went. On the due date, from 09:00 studio time, the card is tried only if that month's reminder went out (`test`, `accepted` or `delivered` on at least one channel); if none did (the server was off for those days, or the reminder is still waiting, was stopped, refused or unclear), the month is not taken, noted for staff and the client's record, and stays unpaid. Every try is a row in `membership_charges` (migration 30) first, after the membership, agreement, saved card and month are checked again and the `plan-renew` is rehearsed. The row's ID is the provider's idempotency key, and a unique index allows one live or successful try per membership and month. A confirmed payment is recorded as `plan-renew` by `card` with the provider's reference, the processor and the month, in one transaction with the row; if it cannot land (the plan ended while the card was out) the row becomes `review` and nothing is forced in. A declined card is tried again 1, 3 and 7 days after the first try at 09:00, unless the month has ended; after the fourth decline SALEANE stops, the client gets a `plan_declined` email or text, and staff see it. Paying the month by hand, ending the plan, removing the card or turning card payments off stops further tries. An unclear answer becomes `unknown`, blocks hand records, refunds, turning off and removing that card for the membership, and is never retried by itself: staff choose "Check again", which repeats the same request under the same key. A try left `started` by a stop or crash becomes `unknown` on the next pass. Sample studios never charge or remind.

Ending a membership whose current month the card paid sends the money back to that card through the provider (`POST …/plan-cards/:holdingId/end` with an `Idempotency-Key`), capped at the unused part of that payment; the membership ends with the refund once the provider confirms it, and the same page refuses a refund recorded by hand for that month. Restoring a backup pauses card payments for every studio with an open agreement and marks tries still waiting as `unknown`, until the owner or a manager has checked the provider and turns them back on. Card payments are never counted as cash in the till, and accounts exports list them as card payments through SALEANE, marked as test payments in test mode.

### Booking through ChatGPT or Claude (Stage 5)

A studio's owner can let an AI assistant a guest is talking to book a visit for them (`ai-booking` command, owner only, off by default; sample studios may try it). `server/aiBooking.ts` is a remote MCP server for each studio at `POST /api/mcp/:slug`: JSON-RPC 2.0 over the streamable HTTP transport, answered with `application/json`, protocol versions 2025-11-25, 2025-06-18 and 2025-03-26. It is handled before the Origin and JSON checks for SALEANE's own pages, as the Google partner route is. `initialize` returns an `Mcp-Session-Id`, which every later message must carry (400 without it, 404 once it has ended or the server restarted); `DELETE` ends it. It speaks `initialize`, `notifications/initialized`, `ping`, `tools/list` and `tools/call`; notifications and answers get 202, batches and messages that are not JSON-RPC are refused, and a browser `Origin` from anywhere else gets 403. The four tools are `studio_details`, `list_treatments`, `find_free_times` and `book_time`. They read only what the booking page shows: opening hours, the treatments guests can book online without a deposit or patch test, professionals' names and free times. `book_time` needs the guest's name, email and phone and `guest_confirmed: true`, then holds and books through the booking page's own `holdTime` and `bookHeld` (source `online`, channel `chatgpt`, `claude` or `assistant`, audit action `ai-booking.*`). It never assumes marketing consent and returns the visit with the guest's private link. The same request on the same connection within 15 minutes of the hold returns the same visit with a fresh link, so a retry books once. Online booking off, a studio locked for an unpaid bill, or the owner's choice off answers 404. Calls are limited per address (`ai-booking` 120 and `ai-booking-tool` 40 every 10 minutes, plus the booking page's own hold and booking limits). `GET /api/workspaces/:orgId/ai-booking` gives the owner `{mode,reachable,address,sample}`.

### Connected software (V5)

Owners can point SALEANE at other software (a Zapier hook, their own system) and choose which diary events it hears about. A listener on `persist` compares the studio record before and after each saved change and writes one `connection_deliveries` row per event and connection inside the same transaction. The delivery loop claims a row as `unknown` before posting, signs the body with the connection's secret (`Saleane-Signature: t=…,v1=HMAC-SHA256`), and records `delivered`, `pending` with the next try, `failed` or `skipped` (turned off before it went out). Guest names and contact details are included only when the owner chose that for the connection. The full contract for the receiving end is in [docs/CONNECTIONS.md](../docs/CONNECTIONS.md).

The owner can also make read-only access keys (`api_keys`, stored as a SHA-256 hash with a short public prefix for lookup). `/api/v1/*` accepts only `GET` with `Authorization: Bearer sal_…`, needs no session or Origin, reads the studio through `systemOrg`, checks the key's scopes, records when it was last used and is rate limited per key. Revoking a key stops it on the next request. A key can carry a `location_id` (it then reads only that location's visits and the menu, and stops if the location closes) and an `ends_on` day in the studio's time (migration 22).

| ----------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------ |
| `SALEANE_CONNECTIONS`               | `test`  | `test` signs and logs each event and sends nothing; `live` posts to the owner's HTTPS addresses.                   |
| `SALEANE_CONNECTIONS_ALLOW_PRIVATE` | unset   | `1` lets `live` reach `http://`, localhost and private addresses, for trying a receiver on your own computer only. |

## Authority and request contract

Passwords use salted scrypt; session cookies carry random tokens whose hashes are stored in SQLite. Cookies are HttpOnly, SameSite Strict and expire after 12 hours; HTTPS uses Secure. A password change revokes all previous sessions. Authenticated writes require `X-CSRF-Token` from registration, login or `GET /api/session`. All writes require the exact Origin and JSON. Host validation, cross-site rejection, request limits, bounded JSON bodies and generic server errors apply. No authentication secret appears in workspace or audit responses.

Schema changes are numbered, forward-only migrations in `database.ts`; each step commits with its version record, and a database written by an unknown version is refused. Migration 1 contains accounts, memberships, session hashes, invitations, organisation snapshots, command receipts, guest holds and audit events. A write checks membership and command permission, then executes synchronously inside `BEGIN IMMEDIATE`, saves the validated snapshot with its revision, records its receipt and audit, and commits. Competing stale revisions return 409. The command schema and transition rules are shared with the operating domain; the server supplies the authenticated actor and clock. Catalogue price, duration and buffer are appointment snapshots. Active guest holds participate in both desk booking and rescheduling, including exact room allocation.

For `POST /api/workspaces/:orgId/commands`, send `{revision,command}` and a unique `Idempotency-Key` of 8–100 safe characters. Retrying the same intent/key returns the original record ID and current authorised state. Reusing a key for another intent returns 409. Current membership and permission are checked before receipt replay, so a saved key does not preserve revoked access. The key is scoped to the account and organisation. Responses include `{ok,state,recordId}`; replay adds `replayed:true`. Validation, availability and role errors never partially publish a snapshot.

Owner access governs team changes, organisation identity and tax policy. Managers can manage operating configuration, catalogue and refunds. Reception access includes the workspace, clients, calendar and checkout ledger needed by the front desk. Practitioner provisioning and reads are deliberately disabled until an assigned-client projection is implemented and tested. There is no owner transfer UI or multiple-owner provisioning in this candidate.

Workspace input is `{name,region:'UK'|'US',locationName,address?,timeZone?,sample?}`. UK uses Europe/London; US accepts supported American time zones and defaults to America/New_York. `sample:false` is the default: a new business starts with no fictional clients, services, appointments, money or inventory. `sample:true` creates an isolated sandbox fixture owned by the new account. It cannot become a live workspace by changing browser state.

Hold protection: a hold lapses after five minutes. One visitor (network address, stored only as a per-process salted hash) keeps at most two unbooked holds per studio; a newer hold replaces the oldest, and a refused hold leaves the earlier ones in place. `replaces` releases the guest's previous hold first. Each address may create six holds a minute and thirty an hour (429 beyond that). A studio carries at most the larger of 8 or three per active professional unbooked holds at once (429 "Many guests are choosing times right now"); booked or expired holds stop counting. When the studio switched the bot check on and keys are configured, a hold needs a passing Turnstile token in `botCheck`; a missing, failed or unverifiable token returns 403 before anything is written. Behind a reverse proxy every guest shares the proxy's address, so these per-address limits need a trusted forwarded-address setting before hosting.

Public holds pin service duration, buffer, price, deposit requirement, resource type, professional and resource. A service edit, archive, closure, conflict or expiry invalidates an unconsumed confirmation. Releasing a hold does not cancel an appointment or erase its receipt. Completed confirmation retries preserve the receipt after hold expiry. Disabling public booking hides public routes. The public booking page itself collects no money. A local booking's deposit requirement is recorded, and the guest can pay it afterwards from the private link to their visit (PILOT-02); no deposit receipt or settlement is invented before the provider confirms one. Only sandbox bookings simulate deposits. Locally recorded cash/external-card receipts are staff declarations; an external card reference is required and no provider verification is claimed.

## Backup and recovery

After the server/tool build, the CLI supports these actions (replace the example paths with your database and fresh destination):

```sh
npm run db:backup -- backup .saleane-data/saleane.sqlite work/backup-2026-10-06.sqlite
npm run db:backup -- verify work/backup-2026-10-06.sqlite
npm run db:backup -- restore work/backup-2026-10-06.sqlite work/recovered-2026-10-06.sqlite
```

`db:backup` runs `node server-dist/backup.js`. The backup entry is built after the host entry with `vite build --ssr server/backup.ts --outDir server-dist --emptyOutDir false`.

Backup uses SQLite `VACUUM INTO` for a consistent snapshot, including committed WAL data while the source is open. Source validation and copy validation check integrity, foreign keys, supported migration version, required tables and every organisation snapshot/revision. The copy is private and published atomically. Existing destinations, even empty files or paths with SQLite companions, are refused. The tool never changes the source or overwrites a running database.

Restore requires a fresh destination and clears sessions, invitations, guest holds and guest manage links so stale credentials and reservations cannot be resurrected. Nothing that reaches outside the studio comes back by itself either: access keys for other software are revoked, connected software is turned off (its pending deliveries are marked not sent), Instagram, Facebook and WhatsApp accounts go back to waiting for confirmation, and queued messages that were still pending are held as "unknown", because they may already have gone, and membership card payments pause until the owner or a manager has checked the provider (Stage 1). The owner turns each one back on, and the team checks a held message before sending it again. Two-step recovery codes come back used, so each person makes new ones. The restore result reports how many of each were held back. Accounts, memberships, workspace state, command receipts and prior audit are preserved; each workspace gets a `workspace.restored` audit entry. Stop the application, verify the recovered path, then explicitly set `DB_PATH` to it and start one host. No automatic replacement or configuration change occurs. Backups contain client and account data and need appropriate private storage; off-device encrypted backup, retention and disaster recovery remain release gates.

## Verification and remaining gates

`vitest run --config server/vitest.config.ts` runs Node-only API/database tests using `.inject()` and disposable database files. It covers request/auth boundaries, tenant access, revision races, idempotency and role revocation, file reopen, public DTO privacy, held-resource allocation, hold release/expiry/replay, changed catalogue contracts, zero automatic local deposits, and live-WAL backup/fresh-path restore. No provider/network side effects occur. Parent release evidence records the separately exercised browser and full-app build/lint checks; this API test suite does not prove them.

This candidate has one location per workspace and transactional JSON snapshots, not a qualified multi-site hosted database. It has no password reset/email verification/MFA, clinical records, provider reconciliation, online payment, real communications delivery, deployment monitoring, external backup, automated retention, migration rollback or production load qualification. The local rate limiter is process-local. SQLite is experimental in the tested Node runtime. Remote hosting, practitioner projection, real service connections, tax/legal acceptance, data migration and operational recovery are explicit later gates. Saleane Clinical remains a separate compliance boundary.

Primary references: [Node 22 SQLite API](https://nodejs.org/download/release/v22.22.0/docs/api/sqlite.html), [SQLite VACUUM INTO](https://www.sqlite.org/lang_vacuum.html).
