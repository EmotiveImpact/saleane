## What actually works

Version **1.0.0-rc.1** connects Today → Calendar → Client → Appointment → manual Checkout → Rebook → Business intelligence. There are two modes: the preserved fictional browser demo with a fixed 6 October 2026 date, and authenticated local studios with current venue time and SQLite authority.

Local accounts, tenant memberships, manual invitations, treatments/qualified professionals/resources, hours/closures/tax setup, public availability with exact-room holds, the visit lifecycle, client timeline, manual receipts/deposits/refunds, unsent drafts, bounded CSV imports and backup/restore are implemented. Empty UK/GBP and US/USD studios can be created through `/account`; a new studio starts closed on Sunday with online booking off, and Today lists what is left to set up. Professional catalogue entries do not confer login access by themselves.

Merged on top of that, all built locally and in test mode where a provider would be needed:

- LOCAL-01 to LOCAL-05 and OFF-01: practitioner access ("Your day"), guest manage links (cancel, and since 9 October move), privacy and the data lifecycle, schedule administration, a qualification pass, and the read-only offline day sheet.
- Pilot basics (PILOT-01 to 04): visit messages, saved cards, card payments and deposits in test mode, switching from another system, one published price.
- V1.5: gift cards, packages and memberships, patch tests, forms, consultations, waitlist (with pass-on), due back and aftercare, birthday and "we miss you", reviews, missed-call text-back, the Inbox.
- V2: stock and retail at the till, commissions, tips, rota and time off, chair and room rent, supplier orders, accountant exports, several locations.
- V3 core: Ask SALEANE (morning brief, warnings, booking and cancelling by chat, cover plans), smart insights and specials.
- V4 in test mode: the AI receptionist on the booking page, texts, Instagram, Facebook and WhatsApp, and Book with Google.
- V5: the whole business view, regions and regional managers, general managers, requests that pass up, branch visits, client areas and maps, brand rules, several brands, month-end estimate, benchmarking, branch map, partner access keys, automatic checks.
- The 9 October app review (48 items) fixed the problems it found and polished the daily screens; see the changelog entry of that date.
- NEXT-03: a forgotten password link and an email confirmation link (migration 23, `server/accountMail.ts`). With email in test mode nothing is sent: the link is written in the server log and the record says `test`.
- NEXT-04: two-step sign-in with an authenticator app and recovery codes (`server/twoStep.ts`, `src/components/TwoStepSettings.tsx`). Authenticator keys sit in SQLite like connection secrets; a hosted database should encrypt them at rest.
- NEXT-05: who changed what, for the owner (`src/domain/changeRecord.ts`, `server/routes/changes.ts`, migration 25). `persist` works out which details of the record changed and stores them with the audit entry; values are kept only for numbers, money, times, dates, yes-or-no settings and links, never for client records or typed wording. A new command fails to compile until it has words in `commandWords`, and a test fails if a server action has none.
- NEXT-02: studios paying for SALEANE (`server/billing.ts`, `src/domain/billing.ts`, `src/components/PlanBilling.tsx`, migration 26). Each real studio has a `studio_plans` row from the moment it is made (14-day trial, no card); `run()` (every minute) warns, ends trials, renews, retries and makes studios read only. The price and AI allowances live only in `src/domain/pricing.ts`; `ctx.plans.allowance(org)` gives every AI route its allowance for the studio's locations, Plus and state. Billing uses its own provider (`SALEANE_BILLING_PROVIDER`), never the studio's own card account.

There is no hosted service, real card capture/refund, sent email/SMS (so password and confirmation links reach only the server log), AI supplier, map service, production identity qualification, verified guest identity (manage links are bearer capabilities copied by hand), comprehensive privacy programme or real studio pilot. Stable 1.0 requires the roadmap’s release gates, not a cosmetic version change.

## Invariants that must survive

- Validate membership, command permissions, expected revision and scoped request keys server-side, in transactions. Never accept client role claims or use UI hiding as access control.
- Existing whole-studio BusinessState reads are unsuitable for practitioner access. Practitioners receive only the `PractitionerView` from `src/domain/practitioner.ts` via `server/projections.ts`, and only `practitionerRefusal`-approved commands; never widen this by frontend filtering or fabricated empty collections. V5 regional managers (role `regional`, scoped to one region by `memberships.area_id`, migration 20) likewise receive only the `AreaView` from `src/domain/area.ts` and only `areaRefusal`-approved commands (branch visits, and raising and deciding requests for a sign-off, at their own locations; deciding only when the request was routed to their region). Which regions have a regional manager comes from `memberships` on the server and is injected into `request-raise`; a client-sent list is overwritten. V5 general managers (role `general`, scoped to one location by `memberships.location_id`, migration 21) read the studio record through `branchView` (no pay rates; only their location's branch visits and requests) and may use only `GENERAL_ACTIONS` (operations.ts). Every command is checked by `branchRefusal` before it runs and `branchChangeRefusal` after (no visit added or changed outside their location); card payments, card refunds and guest links check the visit's location too. They are manager-like on other routes, so a new route that changes something at a location must check `org.locationId` for them. `orgFor` refuses a regional manager on every route unless the route passes `{ area: true }`; only the workspace read and command routes do, so new routes stay closed to them by default.
- Keep immutable booked service/price/duration/buffer terms, original appointment/client IDs, exact held rooms and linked history. Public holds and desk bookings share availability. Check venue civil time, elapsed duration and DST.
- Operator uncertain requests retain SHA-256-scoped fingerprint → request UUID mappings in tab session storage (200 limit), without command payloads. Storage failure/corruption blocks writes. Reload must not mint a new key for an uncertain operation.
- Guest confirmation retains its exact submitted contact/consent and hold snapshot in tab storage until a definitive outcome. Unknown results remain protected even after hold expiry; do not enable a second booking/edit while recovery is unresolved. Closing the tab is a documented recovery boundary.
- A late async response must not replace a different studio. Revision conflicts load current records without silently resubmitting the initiating draft.
- Browser demo reset must advance persisted revision rather than returning to zero. It is still browser-local storage, not a multi-user transactional authority.
- Money is in minor units with provenance and immutable receipts. Manual payment/refund records explicitly acknowledge already-performed external activity. Cancelled visits retain deposit history; no fabricated fee/refund.
- V5 client areas keep only the first half of a postcode (`client.postcodeArea`, normalised by `postcodeArea` in `src/domain/clientAreas.ts`; a full postcode is cut before it is stored). `clientAreas` names only areas with at least `AREA_MIN_GROUP` (3) clients and folds the rest into "Other areas"; keep that floor in any new view, and never place individual clients on a map. The map (`src/domain/areaMap.ts`, `AreaMap`) draws only `mapAreas` output, which applies the same floor; `mapReady` is true only for sample studios until a real map service adapter exists.
- V5 branch map (`branchMap` in `src/domain/branchMap.ts`, `BranchMap`): places each location with `placeCentre` and shows only `wholeBusiness` figures. The regional manager's `AreaView.map` is built with their region's location ids; keep it to those, and keep it null when `mapReady` is false.
- V5 brands together (`GET /api/group`, `src/domain/brandGroup.ts`, `BrandsTogether` on /account) reads every studio the account owns and returns totals only, from `wholeBusiness`. Keep it to `role === 'owner'` memberships and never return client, visit or receipt records from it; totals are added only within one currency and never mix sample with real studios. Each brand stays its own studio; nothing is shared between them.
- V5 benchmarking (`GET /api/workspaces/:id/benchmark`, `server/routes/benchmark.ts`, `src/domain/benchmark.ts`): only owners turn `operations.benchmark.sharing` on, and only a sharing studio gets a comparison. Peers are other sharing studios in the same region and of the same kind (sample or real), grouped by owner (`perOwner`; the requesting owner's studios are left out). Keep the response to the rounded (`coarse`) spread of `studioMeasures`, return `comparison: null` below `BENCHMARK_MIN_STUDIOS` (10) owners, and never return a peer's id, name or count.
- V5 partner keys (`server/partnerApi.ts`, migration 22): a key with `location_id` may hold only `LOCATION_SCOPES` and must filter every location-bound read by it; clients and takings stay whole-studio scopes. `ends_on` is checked against `businessDate` on every request. Keep every v1 endpoint free of client names unless it needs `clients:read`.
- V5 automatic checks (`src/domain/groupChecks.ts`, `operations.groupChecks`, owner-only `group-checks` command): `groupAlerts` is computed on read and must stay read-only (no commands, no messages). `AreaView.alerts` is built with the region's location ids only; the regional morning summary's branch-visit line uses `groupCheckSettings(s).visitDueDays`.
- Waitlist pass-on (`unansweredOffers` in `src/domain/waitlist.ts`, `PassOnOffers` on /waitlist) is read-only: it only suggests. Passing on uses the ordinary `waitlist-offer` command, so the new offer is a draft awaiting approval; never send or withdraw anything from it. An offer counts as unanswered from its `approvedAt`, not from delivery.
- V5 house rules (`operations.houseRules`, owner only) are enforced in the `service` command by `serviceRuleRefusal` (`src/domain/brandRules.ts`); keep any new path that writes `locationPrices` or `notOfferedAt` going through it. Setting a rule never rewrites existing treatments; `ruleBreaches` lists them. Studio colours are `operations.look` and reach guests through the public booking payload.
- A guest moves their own visit only through `POST /api/guest/move` (`server/routes/guest.ts`, `src/domain/guestMove.ts`): the same treatment at the same location, with the same professional or anyone qualified, not within `GUEST_CANCEL_CUTOFF_HOURS` of the visit and at most `GUEST_MOVE_DAYS` ahead. The server rechecks the time against desk bookings and online holds, keeps the booked terms, and the open link follows the visit; a visit the desk moves keeps its open links too (`followGuestLinks`).
- Messages passed on from the booking page chat always wait unmatched for the team; never match a chat sender to a client by an email or number they typed. Texts from a number already on file still match.
- A newly added Instagram, Facebook or WhatsApp account is stored unconfirmed (`unconfirmed:<orgId>:<accountId>`) until the owner proves it is theirs, and message routing never matches an unconfirmed id. Once one studio confirms an account, no other studio can add it.
- Requests record who raised them (`raisedById`, from the session, never from the browser). A regional manager's own request goes to the owner, and they cannot decide a request they raised.
- Only the owner and managers, or a general manager for a client who visits their location, may remove a saved card (`mayRemoveSavedCard`). `orgFor` refuses a general manager whose location has closed on every route.
- Gift cards, packages and memberships record the location that sold them; rent and other takings are counted on the studio's own day, never the UTC day.
- Each command inside a batch is validated on its own before anything reads it. Outgoing connections treat NAT64 addresses as private.
- Imports are bounded and reviewed, source-attributed, never infer marketing consent and never auto-merge identities on email. Queued communications remain unsent.
- NEXT-02 billing: claim an invoice (`open` → `charging`) before asking the card service, use `<invoiceId>.<attempt>` as the idempotency key, and ask again with the same key when the answer is unclear; never mark a bill paid without the provider's answer, and in test mode say "settled in test mode", never "paid". A read-only studio is refused writes centrally by `billing.guard` in `server/app.ts` (402 with `readOnlyMessage`); keep its allowlist to paying, privacy exports, removing people, revoking keys and links and pausing connections, and keep guest booking working. Nothing is deleted when a studio stops. Sample studios have no plan and are never charged. A restore marks open bills `unknown` and sets `held_at` on every plan; `reconcile` in `run()` then asks the card service (`provider.charges`, by the `studio` mark every charge carries) what it took, marks those bills paid or rebuilds them, owes again what it did not take with a fresh attempt number, and only then clears `held_at`. Keep every charge's marks, and never release a held plan without that answer. A read-only studio locks at `lock_at` (30 days after the last day paid for; migration 27): `billing.guard` then refuses everyone but the owner even reads, the owner keeps only the record, paying, privacy exports and the safety actions, `publicOrg` closes online booking and the AI receptionist, and access keys read nothing; a paid month clears the lock. Guest manage links keep working for bookings already made.
- Backup is consistent with WAL; restore uses a fresh path and revokes sessions/invitations/holds/guest links. It also holds back everything that reaches outside the studio: access keys are revoked, connections turned off, social accounts set back to unconfirmed and pending messages held as unknown until the team checks them. Keep databases and sidecars outside static roots and Git.

## Local operating instructions

Use Node 22.13+ (22.22.3 verified), npm and the existing lockfile. Dependencies are already installed in this checkout; avoid needless installation, copies or new worktrees because local disk has been very tight. Check free space first if generating large outputs. Never delete user data to make room.

Check for the existing process on 127.0.0.1:5173 before starting anything. Keep exactly one server. `npm run dev` provides development UI/API; `npm run check` runs lint, frontend/server tests and builds; `npm start` serves the built UI/API after stopping any development server. Static `npm run preview` does not provide the API. Use `/account` for local accounts and `/book/:slug` for guest booking. Do not commit account passwords or local session data.

Default private database: `.saleane-data/saleane.sqlite` (ignored). `work/` contains disposable verification material; inspect before deleting. `node_modules`, `dist`, `server-dist`, databases and `.env` must remain untracked. Follow the server runbook for `npm run db:backup` commands rather than copying a live database file.
